# automatic-canary-releases Specification

## Purpose

Provide installable, commit-identifiable npm prereleases for integration testing without changing stable `latest` releases.

## Requirements

### Requirement: Stable release preview remains visible

The system SHALL retain a read-only release preview that runs after pushes to `master` and reports the future stable release without publishing packages or changing repository state.

#### Scenario: Push previews the future stable release

- **WHEN** a commit is pushed to `master`
- **THEN** the release preview performs an Nx stable release dry run
- **AND** it creates no npm version, release commit, changelog update, or Git tag

### Requirement: Canary publication follows checked master changes

The system SHALL run workspace checks before automatically publishing releasable package changes from `master` under the npm `canary` dist-tag.

#### Scenario: Releasable master change passes checks

- **WHEN** a push to `master` contains a releasable package change
- **AND** workspace checks pass
- **THEN** the affected package set is published under the `canary` dist-tag
- **AND** the npm `latest` dist-tag remains unchanged

#### Scenario: Workspace checks fail

- **WHEN** a push to `master` fails a workspace check
- **THEN** no canary package is published by that workflow run

### Requirement: Canary versions identify the source commit

The system SHALL derive the canary prerelease identifier from the first eight hexadecimal characters of `GITHUB_SHA` and SHALL retain the prerelease counter generated by Nx.

#### Scenario: Canary version is generated

- **WHEN** the source commit begins with `a1b2c3d4`
- **AND** Nx resolves the next package version as `0.2.1`
- **THEN** the initial canary version is `0.2.1-canary.a1b2c3d4.0`

### Requirement: Canary versioning is ephemeral

The system SHALL keep canary version changes inside the disposable CI runner and SHALL NOT create or push a canary release commit, changelog entry, or Git tag.

#### Scenario: Canary publication succeeds

- **WHEN** all selected canary packages are published
- **THEN** the source branch, tracked manifests, changelogs, and Git tags remain unchanged

### Requirement: Dependents receive compatible prerelease versions

The system SHALL apply the canary prerelease identifier to packages that Nx bumps because one of their workspace dependencies changed.

#### Scenario: Changed dependency requires dependent publication

- **WHEN** a workspace dependency receives a canary version
- **AND** Nx determines that a dependent package requires a release
- **THEN** the dependent package receives a canary version with the same source SHA identifier
- **AND** its packed workspace dependency range resolves to the compatible published version

### Requirement: Empty release sets do not publish

The system SHALL finish successfully without invoking npm publication when Nx detects no releasable package changes.

#### Scenario: Non-releasable master change

- **WHEN** a push to `master` produces no version changes in package manifests or the workspace lockfile
- **THEN** the canary publish step is skipped
- **AND** the workflow does not query npm for package versions

### Requirement: Unchanged packages are not republished

The system SHALL publish only projects whose package manifest versions changed during canary versioning.

#### Scenario: One package changes

- **WHEN** Nx versions one package and leaves another unchanged
- **THEN** the unchanged package is not published or retagged as canary

### Requirement: Canary retries are idempotent

The system SHALL publish canary packages sequentially, stop after the first failed publish task, and allow the same commit to be retried without choosing a new version.

#### Scenario: Retry after partial publication

- **WHEN** a canary run publishes some package versions and then fails
- **AND** the same source commit is rerun
- **THEN** the workflow skips exact package versions already present in npm without changing their dist-tags
- **AND** Nx attempts to publish only the missing versions using the same canary identifier

### Requirement: Stable publication remains manually controlled

The system SHALL preserve manual stable publication from `master` with Conventional Commit version calculation, changelog generation, release commit and Git tags, and the npm `latest` dist-tag.

#### Scenario: Maintainer dispatches a stable release

- **WHEN** a maintainer dispatches `publish.yml` on the default branch
- **THEN** the stable release job executes the existing checked stable release process
- **AND** the canary job does not execute

#### Scenario: Master receives an ordinary push

- **WHEN** a commit is pushed to `master`
- **THEN** the canary job may execute
- **AND** the stable release job does not execute
